# Knowledge Bank Pipeline: Where Every Field Comes From

This document traces the **full path** each column in the knowledge bank
takes, end to end: which script produced it, which file it passed
through, and — for anything ultimately from Odoo — which live Odoo API
field it is. It complements two other docs rather than repeating them:
[`docs/DATA_DICTIONARY.md`](DATA_DICTIONARY.md) has the full schema of
every intermediate CSV (read that for a field's exact meaning/values);
[`PROJECT_NOTES.md`](../PROJECT_NOTES.md) has the fix history behind
several of the design choices called out below.

As of 2026-09-25, **`boq_coords/` is the priority extraction path** (see
`CLAUDE.md`) — this document focuses on
`knowledge_bank_items_coords.csv`, the file to use for review/analysis.
The differences from the older `quotation_parser_v1.py` path
(`knowledge_bank_items.csv`, still the *main* pipeline's join) are called
out in their own section at the end, since most of the lineage is shared.


## 1. The three streams that converge on the knowledge bank

Every field in the final CSV traces back to exactly one of three
independent streams. They don't talk to each other until the final join.

```
STREAM A — what was quoted (item extraction)
  PDF (Quotation PDFs/raw/...)
    -> boq_coords (coordinate-aware table extraction)
    -> Quotation_Data/03f_structured_coords/quotation_items.csv
                                                                    \
STREAM B — who we quoted it to, and the order itself (Odoo)          \
  Odoo (live XML-RPC, sale.order + res.partner)                       \
    -> odoo_export/export_customers.py                                 \
    -> Quotation_Data/05_odoo_export/sale_orders.csv, res_partners.csv   \
    -> odoo_export/customer_industry_proxy.py                            \
    -> Quotation_Data/05_odoo_export/customer_industry_proxy.csv          |
                                                                           |
STREAM C — the bridge: which document is which Odoo order/customer       |
  boq_coords/match_customers_coords.py                                   |
    (borrows customer/quotation_number from Stream A': see note below)   |
    -> matches against Stream B via RFQ number (exact, then fuzzy)       |
    -> Quotation_Data/06_customer_matching_coords/                       |
       customer_enriched_coords.csv                                     /
                                                                         /
                    ALL THREE JOIN HERE                                /
  knowledge_bank/build_knowledge_bank_coords.py                       /
    reads: Stream A's quotation_items.csv                            /
         + Stream C's customer_enriched_coords.csv                  /
         + Stream B's sale_orders.csv (again, directly)             /
    -> Quotation_Data/07_knowledge_bank_coords/
       knowledge_bank_items_coords.csv
```

**Important wrinkle in Stream C**: `boq_coords` has no document-level
extraction of its own for the *customer name* or a clean
*quotation_number* — those come from a fourth, smaller stream (call it
**Stream A′**): `quotation_parser_v1.py` reads the same documents' text
(via the older `03_preprocessed_text_2/` pipeline) and writes
`Quotation_Data/03_structured_current/quotations.csv`.
`match_customers_coords.py` borrows `customer`/`quotation_number`/
`quotation_date`/`currency` from that file, joined by `source_path`
(falling back to `source_file`), rather than re-parsing the customer name
itself. This is why `boq_coords` still depends on v1 even though it's now
the priority extractor for line items — see §4's `quotation_number`
callout for why this matters.


## 2. Stream A — item extraction (`boq_coords`)

| Stage | Script | Reads | Writes |
|---|---|---|---|
| Manifest | `Quotation PDFs/quotation_pdfs.csv` | (Odoo-exported PDF/RFQ manifest, not generated by this repo) | — |
| Extraction | `boq_coords/__main__.py` (`python -m boq_coords`) | manifest + each PDF's own word/table geometry (`pymupdf`) | `Quotation_Data/03f_structured_coords/quotation_items.csv`, `coords_documents.csv` |

For each manifest row, `__main__.py`:
1. Opens the PDF and runs `boq_coords/rows.py` → `ruled.py`/`banded.py` to
   segment it into a table of rows (column detection via
   `boq_coords/columns.py`, header aliasing via `vocab.py`).
2. Parses each row's price/quantity cells with `boq_coords/money.py`
   (the strict, anchored grammar — this is *why* `price_quality`/
   `arithmetic_check` only exist on this path, not v1's — see
   `DATA_DICTIONARY.md`).
3. Runs `boq_coords/validate.py`'s six rules over each row, flagging
   `validation_error` where applicable.
4. Derives `quotation_number` for the whole document from the manifest's
   own `RFQ` + `Revision_Number` columns — **not from the PDF's own text
   at all** (see the callout in §4).

Every other item-level field (`description`, `make`, `model`, `quantity`,
`unit`, `unit_price`/`total_price` and their raw forms, `item_confidence`,
`parent_item_no`/`item_level`) is produced here, straight from the PDF's
own word coordinates — nothing about them comes from Odoo or from v1.

"Passthrough" means: `export_customers.py`'s `flatten_sale_order()`
writes the raw XML-RPC value straight into the CSV cell (only `False` →
`""`); no lookup or transformation happens for those fields. **Selection**
fields are not separately resolved to a label — on this Odoo database
their stored key already equals their display label for every field
except `x_studio_service_type` (see above), so passthrough already
produces the human-readable value in practice.

`res_partners.csv` (`id`, `name`, `ref`, `email`, `phone`, `street`,
`city`, `state_id_id`/`_name`, `country_id_id`/`_name`) is the same
passthrough pattern, fetched only for the partner ids referenced by the
sale orders above.

`customer_industry_proxy.py` computes, per `partner_id`, the most common
`x_studio_type_of_industry` across all their orders (ties broken by most
recent order date) — this is **not** a live Odoo field, it's a local
aggregation over `sale_orders.csv`.


## 4. Stream C — the bridge (customer matching)

| Stage | Script | Reads | Writes |
|---|---|---|---|
| Match | `boq_coords/match_customers_coords.py` | `coords_documents.csv` (Stream A) + `quotations.csv` (Stream A′, v1) + `res_partners.csv`/`sale_orders.csv`/`customer_industry_proxy.csv` (Stream B) + `customer_name_overrides.csv` (manual) | `Quotation_Data/06_customer_matching_coords/customer_enriched_coords.csv` |

This script does the actual identity resolution, via
`odoo_match_customer.match_customers.match_quotation()` (shared,
unchanged, with v1's own driver) — order of precedence:

1. **Manual override** (`customer_name_overrides.csv`) — highest
   priority, skips everything else.
2. **RFQ number, exact match.** `quotation_number` (borrowed from v1's
   `quotations.csv` — the document's own parsed text, *not*
   `boq_coords`' manifest-derived `quotation_number` field) is
   normalized (`normalize_rfq_number`: uppercase, whitespace-stripped)
   and looked up exactly against `sale_orders.csv`'s
   `x_studio_internal_rfq_assignment_number`. A hit → `RFQ_MATCH`,
   customer/order resolved directly, `customer_match_score = 1.0`.
3. **RFQ number, base-suffix fallback (added 2026-09-25).** If step 2
   found nothing and the RFQ number ends in a revision suffix
   (`R\d+`), strip it and retry once against the base RFQ. A hit here →
   `RFQ_MATCH_BASE` — kept distinct from a direct hit rather than
   blended in, since it's one step less certain (correct in the
   ~1,035-quotation-corpus-wide case this fixed, but relies on Odoo's
   own RFQ field never carrying revisions, which isn't guaranteed for
   every document family).
4. **Fuzzy name matching** (`find_best_match`, only reached if neither
   RFQ step resolved anything) — scores the document's own extracted
   customer name (from v1's `quotations.csv`, again) against every Odoo
   partner name. Produces `EXACT`/`HIGH`/`REVIEW`/`LOW`/`NO_MATCH`.
5. **`MISSING`** — no customer name was even extracted to try matching.

Once a customer is resolved, `build_enrichment_extra()` attaches
`matched_industry` (from `customer_industry_proxy.csv` — the customer's
*aggregate* industry, not this specific order's) and order-history
aggregates (`total_orders`, `total_po_value`, `regions`, ...). If the
match came via RFQ (step 2 or 3), `build_order_extra()` *also* attaches
that **specific** order's own fields
(`matched_order_industry`, `matched_order_po_number`, etc.) — these are
more precise than the customer-level aggregate above, but only present
on an RFQ-matched row.

> ### ⚠️ The `quotation_number` gotcha
>
> There are genuinely **two different `quotation_number` values** in
> play, and only one of them is the CSV column you can see:
>
> - **Cosmetic** — `boq_coords/__main__.py` builds this from the PDF
>   manifest's `RFQ` + `Revision_Number` columns (see §2, and the
>   classifier fixed 2026-09-25 in `quotation_number_for_manifest_row()`
>   for why it isn't a blind concatenation any more). This is what
>   `knowledge_bank_items_coords.csv`'s own `quotation_number` column
>   shows.
> - **Functional** — the value actually used for RFQ matching (step 2/3
>   above) is borrowed from v1's `quotations.csv`, which
>   `quotation_parser_v1.py` extracted by reading the document's own
>   text (a "Ref:"/"Quotation No:" label). It never appears as its own
>   column in the coords knowledge bank — it's absorbed into
>   `matched_rfq_number` after matching succeeds.
>
> The two usually agree, but can diverge (confirmed real case: RFQ
> folder `Q24W10136` containing a document whose own printed quotation
> number was the unrelated `Q24W10132`). If you need to know *why* a row
> matched or didn't, trust `matched_rfq_number` /
> `customer_match_status`, not the `quotation_number` column.


## 5. The final join (`knowledge_bank/build_knowledge_bank_coords.py`)

Reads all three streams' outputs directly — `quotation_items.csv`
(Stream A), `customer_enriched_coords.csv` (Stream C), `sale_orders.csv`
(Stream B, read a **second** time, independently of Stream C) — and
builds one output row per item, joined by `source_path`.

| Output section | Field(s) | Immediate source | Transformation |
|---|---|---|---|
| Lineage | `data_source` | — | literal `"COORDS_ITEM"` |
| | `source_file`, `source_path`, `quotation_number`, `item_no`, `parent_item_no`, `item_level` | `quotation_items.csv` (Stream A) | passthrough |
| Item (raw) | `product_name`, `description`←`description_full`, `make`, `model`, `quantity`, `unit`, prices + raw forms, `total_price_source`, `price_status`, `currency`, `item_confidence`←`confidence`, `validation_error` | `quotation_items.csv` (Stream A) | passthrough (one rename: `description_full`→`description`) |
| Normalized | `make_normalized`, `model_normalized`, `unit_normalized` | this script's own `make`/`model`/`unit` above | `normalize_text_value()` / `normalize_unit()` — case/whitespace/punctuation only, no merging |
| Canonical | `make_canonical(_basis)`, `model_canonical(_basis)`, `unit_class` | `*_normalized` above + `make_aliases.csv`/`model_aliases.csv` (human-curated, gitignored) | `knowledge_bank/canonicalize.py` — rules (split alternates, strip country/legal-form words) then alias-table lookup |
| Product family | `product_family(_basis)` | `model_canonical` then `description` above + `model_family_rules.csv`/`description_family_rules.csv` (human-curated, gitignored) | `knowledge_bank/product_family.py` — model prefix match first, else description phrase match, else blank |
| Derived price | `unit_price_final`, `total_price_final`, `price_basis` | `unit_price`/`total_price`/`quantity` above | `resolve_prices()` (shared with v1) — fills a missing side from the other + quantity when possible, records which happened |
| | `price_quality`, `arithmetic_check` | `price_basis` + `price_status`/`validation_error` above (already computed by `boq_coords/validate.py`+`money.py` at extraction) | pure rollup in this script, no new parsing |
| Customer | `matched_customer_id`, `matched_customer_name`, `matched_industry(_specify_others/_confidence)`, `customer_match_status`, `customer_match_score`, `matched_city`, `matched_state`, `matched_country`, `customer_type`, `regions` | `customer_enriched_coords.csv` (Stream C) | passthrough |
| Order (original 9) | `matched_order_id`, `matched_rfq_number`, `matched_order_industry(_specify_others)`, `matched_order_po_number`, `matched_order_po_value`, `matched_order_quote_status` | `customer_enriched_coords.csv` (Stream C) | passthrough, blank unless RFQ-matched |
| | `order_state`, `firm_or_budgetary` | `sale_orders.csv` (Stream B, direct) | passthrough via the row's own `matched_order_id` lookup |
| Order (21 Odoo Studio fields, added 2026-09-25) | `matched_order_create_date` … `matched_order_reason_for_loss` (full list: see `apply_order_studio_fields()` in `knowledge_bank/build_knowledge_bank.py`, imported and reused unchanged here) | `sale_orders.csv` (Stream B, direct — **not** via Stream C) | passthrough, keyed off the row's own `matched_order_id` |
| Time | `quotation_date_raw` | `customer_enriched_coords.csv`'s `quotation_date` (v1-parsed document date, borrowed via Stream C) | passthrough |
| | `order_date_raw` | `sale_orders.csv`'s `date_order` (Stream B, via the matched order) or `customer_enriched_coords.csv`'s `matched_order_date` | first non-blank |
| | `quotation_date_final`, `date_source`, `date_ambiguous` | the two raw dates above | `resolve_date()` (shared with v1) — Odoo's `date_order` wins when present (`ODOO_ORDER`), else the regex-parsed document date (`PARSED_DOC`), day-first assumed and flagged when both day/month readings are valid |
| | `quotation_year`, `quotation_month` | `quotation_date_final` | string slice |
| Document | `document_currency` | `customer_enriched_coords.csv`'s `currency` (v1-parsed document currency, borrowed via Stream C) | passthrough — kept distinct from the item-level `currency` column above, which is `boq_coords`' own per-item reading and can differ (e.g. one SAR line inside an otherwise-INR quote) |

**Why the 21 Studio fields are sourced directly from `sale_orders.csv`
(Stream B) instead of via `customer_enriched_coords.csv` (Stream C)**:
this was a deliberate choice when they were added, specifically to avoid
touching `match_customers_coords.py`'s own matching logic — the join
that decides *which* order a row belongs to stays completely unchanged;
these 21 fields just read more of that already-matched order's own data.


## 6. Differences on the v1 (non-coords) path

`knowledge_bank/build_knowledge_bank.py` builds
`knowledge_bank_items.csv` the same way, with these differences:

- **Stream A is `quotation_parser_v1.py`**, reading
  `03_preprocessed_text_2/` (cleaned document text) instead of PDFs
  directly, writing `quotation_items.csv` + `quotations.csv` to
  `03_structured_current/`.
- **No Stream A′ borrowing** — v1 *is* the source of `customer`/
  `quotation_number`/`quotation_date`, not a lender to another path. Its
  own `quotation_number` is the one actually used for matching, with no
  separate "cosmetic" value.
- **No `price_quality`/`arithmetic_check`** — v1's price parsing isn't
  done with `boq_coords/money.py`'s strict grammar, so there's no
  equivalent signal to roll up (see `PROJECT_NOTES.md`'s "Known issues"
  for the resulting known defect this leaves unflagged).
- **Has `ODOO_ORDER_ONLY` rows** — one per Odoo order no document
  resolved to at all (`data_source = ODOO_ORDER_ONLY`, item fields
  blank by design). The coords bank has no equivalent rows — deliberate,
  since they'd be identical regardless of which item extractor ran (see
  `build_knowledge_bank_coords.py`'s own docstring).
- Everything in §5 (Stream B, Stream C's matching precedence, the 21
  Studio fields, price/date resolution) is **identical, shared code** —
  `odoo_match_customer/match_customers.py`'s `match_quotation()` and
  `knowledge_bank/build_knowledge_bank.py`'s `apply_order_studio_fields()`/
  `resolve_prices()`/`resolve_date()` are imported and reused unchanged
  by the coords path, not reimplemented.


## 7. Quick answers to "where does X come from?"

| If you're looking at... | It ultimately comes from... |
|---|---|
| `description`, `make`, `model`, `quantity`, `unit`, `unit_price`/`total_price` | The PDF's own printed table, read by `boq_coords` at extraction time. Nothing here is Odoo data. |
| `matched_customer_id`, `matched_customer_name`, `matched_city`/`state`/`country` | Odoo `res.partner`, attached only after a customer match succeeds (§4). Blank city/state usually means the Odoo contact record itself has no value there, not a join failure. |
| `matched_order_*` (any of them, including all 21 added 2026-09-25) | Odoo `sale.order`, via `sale_orders.csv`, keyed off `matched_order_id` — populated **only** when the row matched a *specific* order (RFQ match, exact or base), not just a customer. |
| `matched_industry` (no `order` in the name) | A local aggregation (`customer_industry_proxy.py`) over the customer's *entire* order history — not this specific order. `matched_order_industry` (has `order` in the name) is this specific order's own value. |
| `quotation_date_final` | Whichever of Odoo's `date_order` or the document's own parsed date resolved — check `date_source` to know which. |
| `make_canonical`, `model_canonical`, `product_family` | Never from Odoo or the PDF directly — derived locally from `make`/`model`/`description` by rule tables and human-curated alias tables (`knowledge_bank/canonicalize.py`, `product_family.py`). |
| `price_quality`, `arithmetic_check` | Coords path only — a rollup of signals `boq_coords/money.py`/`validate.py` already computed at extraction, not a new calculation. |
